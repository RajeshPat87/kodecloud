## Runbook

### Objective
Create an Azure Ubuntu VM named `xfusion-vm` in `eastus`, install and start Nginx at boot using cloud-init custom data, open HTTP port 80, and verify public access. [learn.microsoft](https://learn.microsoft.com/en-us/azure/virtual-machines/custom-data)

### Prerequisites
- Azure CLI access with permission to the target subscription and resource group. [learn.microsoft](https://learn.microsoft.com/en-us/azure/virtual-machines/linux/cloudinit-bash-script)
- Existing resource group in East US: `kml_rg_main-5182bff180b54621`, which your successful run validated with `az group show`.[user query]
- A VM size available in `eastus`; your earlier deployment failed because `Standard_DS1_v2` was unavailable in that region at that time. [dev](https://dev.to/cristiansifuentes/azure-vm-deployment-failure-handling-the-skunotavailable-error-like-an-expert-26mg)

### Procedure
1. Create a shell script file, edit it correctly, make it executable, and run it with `./script.sh` instead of `script.sh`, because Bash does not search the current directory by default. [penguin-gym-linux](https://penguin-gym-linux.com/en/articles/troubleshooting/bash-command-not-found-path)
2. Set the subscription, validate the existing resource group, create a cloud-init file that installs and starts Nginx, then create the VM with `az vm create --custom-data` using an Ubuntu image. [learn.microsoft](https://learn.microsoft.com/en-us/azure/virtual-machines/custom-data)
3. Open port 80 with `az vm open-port`, fetch the public IP using `az vm show -d`, wait briefly for cloud-init to finish, and confirm Nginx with `curl -I http://<public-ip>`. [learn.microsoft](https://learn.microsoft.com/it-it/azure/virtual-machines/linux/cloudinit-update-vm)

### Working script
```bash
#!/usr/bin/env bash
set -euo pipefail

SUBSCRIPTION_ID="f0c3bcdd-5ce2-4fa0-8cf3-41559747512b"
RESOURCE_GROUP="kml_rg_main-5182bff180b54621"
LOCATION="eastus"
VM_NAME="xfusion-vm"
ADMIN_USER="azureuser"
IMAGE="Ubuntu2204"
VM_SIZE="Standard_B1s"
CLOUD_INIT_FILE="cloud-init-nginx.yaml"

cat > "${CLOUD_INIT_FILE}" <<'EOF'
#cloud-config
package_update: true
packages:
  - nginx
runcmd:
  - systemctl enable nginx
  - systemctl start nginx
  - systemctl restart nginx
EOF

echo "Setting subscription..."
az account set --subscription "${SUBSCRIPTION_ID}"

echo "Validating resource group..."
az group show --name "${RESOURCE_GROUP}" --query '{name:name,location:location}' -o table

echo "Creating VM ${VM_NAME} in ${LOCATION}..."
az vm create \
  --resource-group "${RESOURCE_GROUP}" \
  --name "${VM_NAME}" \
  --location "${LOCATION}" \
  --image "${IMAGE}" \
  --size "${VM_SIZE}" \
  --admin-username "${ADMIN_USER}" \
  --generate-ssh-keys \
  --public-ip-sku Standard \
  --custom-data "${CLOUD_INIT_FILE}" \
  -o table

echo "Opening HTTP port 80..."
az vm open-port \
  --resource-group "${RESOURCE_GROUP}" \
  --name "${VM_NAME}" \
  --port 80 \
  --priority 1001 \
  -o table

echo "Fetching public IP..."
PUBLIC_IP="$(az vm show -d \
  --resource-group "${RESOURCE_GROUP}" \
  --name "${VM_NAME}" \
  --query publicIps -o tsv)"

echo "VM Public IP: ${PUBLIC_IP}"
echo "Browse to: http://${PUBLIC_IP}"

echo "Waiting 30 seconds for cloud-init and nginx..."
sleep 30

echo "Checking Nginx endpoint..."
curl -I --max-time 30 "http://${PUBLIC_IP}"
```

This procedure aligns with Azure’s documented use of `--custom-data` for Linux cloud-init configuration and the Azure CLI pattern for creating VMs and opening ports. [learn.microsoft](https://learn.microsoft.com/en-us/azure/virtual-machines/linux/cloudinit-bash-script)

## Troubleshooting

### 1. `script.sh: command not found`
This happened because you ran `script.sh` directly; Bash only searches directories in `PATH`, not the current directory, so local scripts must be run as `./script.sh` or with `bash script.sh`. [kodekloud](https://kodekloud.com/blog/how-to-run-sh-shell-scripts-in-linux-fix-command-not-found-permission-denied-errors/)

### 2. `AuthorizationFailed` on `xfusion-lab-rg`
Those errors show your account did not have permission to read network and compute resources under `xfusion-lab-rg`, so that resource group could not be used for this lab session.[user query]  
Switching to the accessible resource group `kml_rg_main-5182bff180b54621` was the correct fix because `az group show` succeeded there and the VM deployment completed afterward.[user query]

### 3. `SkuNotAvailable` for `Standard_DS1_v2`
Azure rejected that size in `eastus` because capacity was unavailable for `Standard_DS1_v2` at deployment time, which is a known regional capacity issue. [learn.microsoft](https://learn.microsoft.com/en-ca/answers/questions/5546441/error-with-creating-a-vm-using-ms-learn-page-exerc)
Using an alternate Standard SKU such as `Standard_B1s` is the recommended workaround when the required region must stay `eastus`. [dev](https://dev.to/cristiansifuentes/azure-vm-deployment-failure-handling-the-skunotavailable-error-like-an-expert-26mg)

### 4. Empty `Browse to: http://`
That happened because the earlier script continued after failed authorization checks and could not retrieve a public IP, so the URL variable was empty and `curl` failed with a bad URL format.[user query]  
Using `set -euo pipefail` and targeting an accessible resource group fixed that behavior by stopping on real errors and producing a valid IP after successful deployment.[user query]

### 5. `wq: command not found`
That happened because `wq` was typed into the shell instead of inside Vim’s command mode; the correct Vim save-and-exit command is `:wq` entered after pressing `Esc`.[user query]

cat > "${CLOUD_INIT_FILE}" <<'EOF'
#cloud-config
package_update: true
packages:
  - nginx
runcmd:
  - systemctl enable nginx
  - systemctl start nginx
  - systemctl restart nginx
EOF

echo "Setting subscription..."
az account set --subscription "${SUBSCRIPTION_ID}"

echo "Validating resource group..."
az group show --name "${RESOURCE_GROUP}" --query '{name:name,location:location}' -o table

echo "Creating VM ${VM_NAME} in ${LOCATION}..."
az vm create \
  --resource-group "${RESOURCE_GROUP}" \
  --name "${VM_NAME}" \
  --location "${LOCATION}" \
  --image "${IMAGE}" \
  --size "${VM_SIZE}" \
  --admin-username "${ADMIN_USER}" \
  --generate-ssh-keys \
  --public-ip-sku Standard \
  --custom-data "${CLOUD_INIT_FILE}" \
  -o table

echo "Opening HTTP port 80..."
az vm open-port \
  --resource-group "${RESOURCE_GROUP}" \
  --name "${VM_NAME}" \
  --port 80 \
  --priority 1001 \
  -o table

echo "Fetching public IP..."
PUBLIC_IP="$(az vm show -d \
  --resource-group "${RESOURCE_GROUP}" \
  --name "${VM_NAME}" \
  --query publicIps -o tsv)"

echo "VM Public IP: ${PUBLIC_IP}"
echo "Browse to: http://${PUBLIC_IP}"

echo "Waiting 30 seconds for cloud-init and nginx..."
sleep 30

echo "Checking Nginx endpoint..."
curl -I --max-time 30 "http://${PUBLIC_IP}"
```

This procedure aligns with Azure’s documented use of `--custom-data` for Linux cloud-init configuration and the Azure CLI pattern for creating VMs and opening ports. [learn.microsoft](https://learn.microsoft.com/en-us/azure/virtual-machines/linux/cloudinit-bash-script)

## Troubleshooting

### 1. `script.sh: command not found`
This happened because you ran `script.sh` directly; Bash only searches directories in `PATH`, not the current directory, so local scripts must be run as `./script.sh` or with `bash script.sh`. [kodekloud](https://kodekloud.com/blog/how-to-run-sh-shell-scripts-in-linux-fix-command-not-found-permission-denied-errors/)

### 2. `AuthorizationFailed` on `xfusion-lab-rg`
Those errors show your account did not have permission to read network and compute resources under `xfusion-lab-rg`, so that resource group could not be used for this lab session.[user query]  
Switching to the accessible resource group `kml_rg_main-5182bff180b54621` was the correct fix because `az group show` succeeded there and the VM deployment completed afterward.[user query]

### 3. `SkuNotAvailable` for `Standard_DS1_v2`
Azure rejected that size in `eastus` because capacity was unavailable for `Standard_DS1_v2` at deployment time, which is a known regional capacity issue. [learn.microsoft](https://learn.microsoft.com/en-ca/answers/questions/5546441/error-with-creating-a-vm-using-ms-learn-page-exerc)
Using an alternate Standard SKU such as `Standard_B1s` is the recommended workaround when the required region must stay `eastus`. [dev](https://dev.to/cristiansifuentes/azure-vm-deployment-failure-handling-the-skunotavailable-error-like-an-expert-26mg)

### 4. Empty `Browse to: http://`
That happened because the earlier script continued after failed authorization checks and could not retrieve a public IP, so the URL variable was empty and `curl` failed with a bad URL format.[user query]  
Using `set -euo pipefail` and targeting an accessible resource group fixed that behavior by stopping on real errors and producing a valid IP after successful deployment.[user query]

### 5. `wq: command not found`
That happened because `wq` was typed into the shell instead of inside Vim’s command mode; the correct Vim save-and-exit command is `:wq` entered after pressing `Esc`.[user query]
