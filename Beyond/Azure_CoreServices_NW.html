Virtual Machines + Scale Sets

Compute that grows and heals itself

Azure Virtual Machines give you on-demand Linux/Windows servers. Virtual Machine Scale Sets (VMSS) manage a group of identical VMs, scale them in and out automatically, and spread them across fault/update domains and Availability Zones.

  • VM — pick size (Standard_B/D/E/F series), OS, managed disks; secured by NSG, SSH keys and managed identity.
  • VMSS holds the instance model and desired capacity; scales on Azure Monitor metrics.
  • Autoscale rules react to CPU / queue depth; health probes replace unhealthy instances.
  • Spread across Availability Zones for HA; use Availability Sets for fault/update-domain isolation.
  • Front VMSS with an Azure Load Balancer or Application Gateway for a fault-tolerant tier.
REFERENCE CARDAzure CLI
# Create a scale set behind a load balancer
az vmss create -g rg -n web-vmss --image Ubuntu2204 \
  --instance-count 2 --vm-sku Standard_B2s --zones 1 2 3 --lb web-lb
# Attach an autoscale profile (2 -> 8 on 70% CPU)
az monitor autoscale create -g rg --resource web-vmss \
  --resource-type Microsoft.Compute/virtualMachineScaleSets \
  --min-count 2 --max-count 8 --count 2
az monitor autoscale rule create -g rg --autoscale-name web-vmss \
  --scale out 1 --condition "Percentage CPU > 70 avg 5m"
Architecture
flowchart LR
    U["Users"] --> LB["Load Balancer / App Gateway"]
    subgraph VMSS["VM Scale Set  (min 2 / max 8)"]
      direction TB
      V1["VM - Zone 1"]
      V2["VM - Zone 2"]
      V3["VM - scaled out"]
    end
    LB --> V1
    LB --> V2
    LB --> V3
    AM["Azure Monitor - CPU 70%"] --> AS["Autoscale rule"] --> VMSS
STAR interview answer
S
SituationA logistics web tier ran on a fixed set of VMs. Peak shipment windows saturated CPU and caused timeouts, and resizing the fleet by hand never caught the spike in time.
T
TaskMake the tier elastic and self-healing so it absorbs surges automatically without paying for peak capacity all day.
A
ActionI moved the workload to a VMSS behind an Application Gateway spread across three Availability Zones, defined the instance model with a custom image to cut boot time, and set an autoscale profile from 2 to 8 instances triggered at 70% CPU. Health probes replaced unhealthy instances automatically, and I codified the whole thing in Terraform.
R
ResultThe tier absorbed peak load with no manual action, timeouts disappeared, unhealthy nodes self-healed across zones, and scaling in overnight cut steady-state compute cost by about a third.
02

Virtual Network (VNet)

Your own isolated, layered network

A VNet is your private, isolated network in Azure. You control address space, subnets, routing and security, and it is the boundary every other resource connects through.

  • Subnets split the VNet into public and private tiers, ideally across zones.
  • NSG = stateful firewall on subnet/NIC; Application Security Groups group NICs by role.
  • NAT Gateway gives private subnets outbound internet without inbound exposure.
  • User-Defined Routes and route tables steer traffic (e.g. through a firewall).
  • Private Endpoints / Service Endpoints reach PaaS (Storage, SQL) privately over the backbone.
  • VNet peering connects VNets; VPN / ExpressRoute connect on-prem.
REFERENCE CARDAzure CLI
# VNet with an app subnet
az network vnet create -g rg -n vnet \
  --address-prefix 10.0.0.0/16 --subnet-name app --subnet-prefix 10.0.1.0/24
# NSG rule + NAT gateway for private egress
az network nsg create -g rg -n app-nsg
az network nat gateway create -g rg -n egress --public-ip-addresses natip
# Private endpoint to a storage account (traffic stays on the backbone)
az network private-endpoint create -g rg -n st-pe --vnet-name vnet \
  --subnet app --private-connection-resource-id <storage-id> --group-id blob
Architecture
flowchart LR
    NET["Internet"] --> AGW["App Gateway - public subnet"]
    AGW --> APP["App subnet - private"]
    APP --> DB["Data subnet - private"]
    APP --> NAT["NAT Gateway"] --> NET
    APP -. private endpoint .-> PAAS["Storage / Azure SQL"]
STAR interview answer
S
SituationAn inherited Azure estate had app servers and databases on the same flat subnet with public IPs, and PaaS storage was reachable over the public internet. A security review flagged it.
T
TaskRe-architect into a secure, tiered VNet enforcing least privilege and passing the audit.
A
ActionI designed a 10.0.0.0/16 VNet with separate app and data subnets across zones, put an Application Gateway in the public tier and everything else private, used NSGs and Application Security Groups to allow only tier-to-tier traffic, added a NAT Gateway for controlled egress, and replaced public PaaS access with Private Endpoints. Diagnostic settings shipped flow logs to Log Analytics.
R
ResultDatabases and storage were no longer internet-reachable, the audit passed, and the private-endpoint traffic stayed on the Microsoft backbone while flow logs gave us the visibility we lacked.
03

App Gateway + API Management

The front door for traffic and APIs

Azure gives you a layered choice: Load Balancer (L4), Application Gateway (L7 with WAF), and API Management (APIM) as a managed front door for APIs with auth, throttling, caching and versioning.

  • Azure Load Balancer — L4 TCP/UDP, high throughput, zone-redundant.
  • Application Gateway — L7 path/host routing, SSL/TLS termination, cookie affinity, built-in WAF.
  • API Management — publish/secure APIs, subscription keys, rate limits, JWT validation, caching, versions.
  • APIM policies transform requests/responses and enforce quotas at the edge.
  • Front private backends (AKS, Functions, VMs) through App Gateway + APIM.
REFERENCE CARDAzure CLI
# Application Gateway (L7) with WAF
az network application-gateway create -g rg -n appgw --sku WAF_v2 \
  --vnet-name vnet --subnet appgw --public-ip-address agw-ip --priority 100
# API Management instance
az apim create -g rg -n org-apim --publisher-email dev@org.com \
  --publisher-name Org --sku-name Developer
Architecture
flowchart LR
    U["Users"] --> AGW["App Gateway - L7 + WAF"]
    AGW --> B1["Backend pool - /cart"]
    AGW --> B2["Backend pool - /orders"]
    C["API clients / partners"] --> APIM["API Management - keys, quota, JWT"]
    APIM --> FN["Functions / AKS"]
STAR interview answer
S
SituationWe were splitting a monolith into services on AKS and also had to expose a partner API, but there was no clean L7 routing and no way to protect the public API from abuse.
T
TaskRoute traffic to the right service and expose a secured, rate-limited partner API.
A
ActionI put an Application Gateway with WAF in front of the services for path- and host-based routing and TLS termination with a Key Vault certificate, and fronted the public API with API Management using subscription keys, rate-limit and quota policies, JWT validation, and response caching, reaching private backends inside the VNet.
R
ResultRouting became declarative, TLS was offloaded, the WAF blocked common attacks, partner abuse was throttled at the edge, and API caching noticeably reduced backend load.
04

Front Door + Azure DNS

Global delivery and smart DNS

Azure Front Door is a global entry point and CDN that terminates at the edge and routes to the fastest healthy backend. Azure DNS hosts your domains, and Traffic Manager adds DNS-level routing/failover across regions.

  • Front Door — global anycast, edge caching, TLS offload, WAF, latency-based routing, health probes.
  • Azure CDN caches static content near users (or use Front Door's caching).
  • Azure DNS — authoritative hosting; alias records to Azure resources.
  • Traffic Manager — DNS routing methods: priority, weighted, performance, geographic.
  • Together: DNS resolves to the right endpoint, Front Door delivers it fastest and safest.
REFERENCE CARDAzure CLI
# Front Door (Standard) profile + endpoint
az afd profile create -g rg --profile-name fd --sku Standard_AzureFrontDoor
az afd endpoint create -g rg --profile-name fd --endpoint-name web
# DNS zone + Traffic Manager (performance routing)
az network dns zone create -g rg -n example.com
az network traffic-manager profile create -g rg -n tm \
  --routing-method Performance --unique-dns-name org-web
Architecture
flowchart LR
    U["Users - global"] --> DNS["Azure DNS / Traffic Manager"]
    DNS --> FD["Front Door - edge + WAF"]
    FD --> O1["Backend - region A"]
    DNS -. failover .-> O2["Backend - region B"]
STAR interview answer
S
SituationA customer portal ran in a single region. Users in other geographies saw high latency, and a regional problem could take the portal offline entirely.
T
TaskCut global latency and add automatic failover so one region is never a single point of failure.
A
ActionI put Azure Front Door in front of the app with edge caching, TLS offload and WAF, enabled latency-based routing across two regional origins with health probes, and used Azure DNS with Traffic Manager for DNS-level failover between regions.
R
ResultLatency dropped for international users as the edge served most requests, origin load fell, and during a later regional incident traffic failed over automatically with no manual action.

Azure SQL + Cosmos DB

Pick the right database for the job

Azure SQL Database is a managed relational engine with built-in HA, automated backups and point-in-time restore. Cosmos DB is a globally distributed, multi-model NoSQL service with single-digit-millisecond latency and turnkey multi-region writes.

  • Azure SQL — DTU or vCore tiers, active geo-replication, auto-failover groups, PITR.
  • Azure Database for PostgreSQL/MySQL for open-source relational workloads.
  • Cosmos DB — serverless or provisioned RU/s, global distribution, five consistency levels, multiple APIs (Core/SQL, Mongo, Cassandra).
  • Choose SQL for relational/ACID; Cosmos for global scale and low-latency key-value/document.
  • Encrypt at rest by default; use Private Endpoints and managed identity for access.
REFERENCE CARDAzure CLI
# Azure SQL logical server + database
az sql server create -g rg -n org-sql --admin-user sqladmin --admin-password '<pwd>'
az sql db create -g rg -s org-sql -n appdb --service-objective S1 \
  --backup-storage-redundancy Geo
# Cosmos DB account, multi-region
az cosmosdb create -g rg -n org-cosmos --kind GlobalDocumentDB \
  --locations regionName=eastus --locations regionName=westeurope \
  --default-consistency-level Session
Architecture
flowchart LR
    APP["Application"] --> PE["Private Endpoint"]
    PE --> SQL["Azure SQL - primary"]
    SQL -. geo-replica .-> SEC["Failover group - region B"]
    APP --> COS["Cosmos DB"]
    COS --> R1["Region A - write"]
    COS --> R2["Region B - write"]
STAR interview answer
S
SituationReporting queries were hammering the primary Azure SQL database and slowing transactions, and a session/cart store on the same SQL DB struggled during spikes.
T
TaskProtect transactional performance and give the cart a globally scalable, low-latency store.
A
ActionI set up an auto-failover group with active geo-replication for HA on Azure SQL and pointed read-heavy reporting at a readable secondary, tuned PITR and geo-redundant backups, then moved sessions and cart to Cosmos DB with Session consistency and a deliberate partition key, connecting both privately via Private Endpoints.
R
ResultTransaction latency recovered immediately, failover tested cleanly, the cart handled spikes at single-digit-millisecond latency, and offloading reads to the secondary removed the reporting bottleneck.

Azure Functions + Serverless

Run code, not servers

Azure Functions runs event-driven code without managing servers. It scales automatically and, on the Consumption plan, you pay only for execution time and resources used.

  • Triggers & bindings: HTTP, Timer, Blob, Queue, Service Bus, Event Grid, Cosmos DB change feed.
  • Plans: Consumption (scale to zero), Premium (no cold start, VNet), Dedicated (App Service).
  • Built-in autoscaling; use Durable Functions for stateful orchestrations.
  • Secure with managed identity, Key Vault references and VNet integration.
  • Watch cold starts on Consumption — use Premium/pre-warmed instances on latency-sensitive paths.
REFERENCE CARDAzure CLI
# Create a Python function app on the Consumption plan
az functionapp create -g rg -n org-func \
  --consumption-plan-location eastus --runtime python \
  --functions-version 4 --storage-account orgstore
# Deploy code
func azure functionapp publish org-func
Architecture
flowchart LR
    BLOB["Blob Storage event"] --> FN["Azure Function"]
    HTTP["HTTP trigger"] --> FN
    EG["Event Grid / Service Bus"] --> FN
    FN --> COS["Cosmos DB"]
    FN --> OUT["Storage / Service Bus"]
    FN -. failures .-> DLQ["Dead-letter / poison queue"]
STAR interview answer
S
SituationA document-processing pipeline ran on always-on App Service instances that sat idle most of the day but fell behind during upload bursts.
T
TaskReplace it with something that scales to zero and still absorbs bursts.
A
ActionI wired a Blob-created trigger to an Azure Function that processed the file and wrote metadata to Cosmos DB, used a managed identity and Key Vault references for secrets, added a poison-message queue with retries, and put the latency-sensitive path on a Premium plan to eliminate cold starts.
R
ResultCompute cost dropped sharply since we paid per execution, upload bursts were absorbed automatically, and we removed all server patching and scaling overhead.

Service Bus + Event Grid

Decouple, buffer, and fan out

Azure Service Bus is enterprise messaging with queues and topics for reliable, ordered, transactional processing. Event Grid is a lightweight pub/sub event router. Together they enable scalable, reliable, event-driven systems.

  • Service Bus queues — point-to-point, at-least-once, sessions for FIFO, dead-letter, duplicate detection.
  • Service Bus topics/subscriptions — pub/sub with subscription filters.
  • Event Grid — reactive event distribution from Azure services and custom topics, with retries and dead-lettering.
  • Storage Queues for simple, high-volume queueing.
  • Pattern: publish an event, fan out to multiple subscribers, each processed independently and reliably.
REFERENCE CARDAzure CLI
# Service Bus namespace + queue
az servicebus namespace create -g rg -n org-sb --sku Standard
az servicebus queue create -g rg --namespace-name org-sb -n orders \
  --enable-dead-lettering-on-message-expiration true
# Event Grid custom topic
az eventgrid topic create -g rg -n order-events -l eastus
Architecture
flowchart LR
    SRC["Order service"] --> TOP["Service Bus topic / Event Grid"]
    TOP --> S1["Sub - inventory"] --> W1["Worker"]
    TOP --> S2["Sub - notifications"] --> W2["Email / SMS"]
    TOP --> S3["Sub - analytics"] --> W3["Consumer"]
    S1 -. poison .-> DLQ["Dead-letter"]
STAR interview answer
S
SituationAn order service called inventory, notifications and analytics synchronously, so one slow or failing downstream failed the whole checkout.
T
TaskDecouple the flow so an order is accepted instantly and each downstream processes independently and reliably.
A
ActionOn each order I published to a Service Bus topic and fanned out to subscriptions for inventory, notifications and analytics, each with its own consumer. I used sessions where ordering mattered, tuned lock duration and max-delivery-count, enabled dead-lettering and duplicate detection, and applied subscription filters so consumers only got relevant events.
R
ResultCheckout became instant and resilient — a downstream outage no longer failed orders because messages buffered and retried — and new consumers were added later with zero changes to the producer.

Azure Monitor + Activity Log

See it, alert on it, audit it

Azure Monitor collects metrics and logs, alerts and visualizes them; Log Analytics is the query store and Application Insights the app-level APM. The Activity Log records control-plane operations for governance and auditing.

  • Metrics + alert rules notify via Action Groups (email, SMS, webhook, PagerDuty, Logic App).
  • Log Analytics centralizes logs; query with KQL; Container Insights covers AKS.
  • Application Insights — distributed tracing, dependency and request telemetry.
  • Activity Log — who did what on the control plane; route to Log Analytics/Storage for retention.
  • Set meaningful alerts to avoid fatigue; monitoring is about acting on data, not just collecting it.
REFERENCE CARDAzure CLI
# Log Analytics workspace + metric alert
az monitor log-analytics workspace create -g rg -n org-law
az monitor metrics alert create -g rg -n high-cpu \
  --scopes <vmss-id> --condition "avg Percentage CPU > 80" \
  --action <action-group-id>
# App Insights
az monitor app-insights component create -g rg --app org-ai -l eastus
Architecture
flowchart LR
    RES["VMSS / AKS / SQL / Functions"] --> MON["Azure Monitor - metrics & logs"]
    MON --> AL["Alert rule - CPU / 5xx / latency"]
    AL --> AG["Action Group"] --> N["Slack / PagerDuty / Email"]
    RES --> ACT["Activity Log - control plane"] --> LAW["Log Analytics - retention"]
STAR interview answer
S
SituationIncidents were being reported by users before we noticed them, and there was no reliable record of who changed what across subscriptions.
T
TaskBuild proactive monitoring and alerting plus a compliance-grade audit trail.
A
ActionI centralized telemetry into Log Analytics, instrumented apps with Application Insights for distributed tracing, created metric and log alerts on CPU, 5xx and latency wired to Action Groups paging Slack and PagerDuty, enabled Container Insights for AKS, and routed the Activity Log to Log Analytics with a diagnostic setting for long-term retention.
R
ResultMean time to detect and recover dropped sharply, we caught issues before customers did, and the Activity Log gave us the audit trail needed for compliance and post-incident RCA.

High-yield Q&A

NSG vs Azure Firewall
NSG is a free, stateful allow/deny filter on subnets/NICs for basic L3-L4 rules. Azure Firewall is a managed, stateful network firewall with FQDN filtering, threat intelligence and centralized policy for whole VNets.
Availability Set vs Availability Zone vs VMSS
Availability Set spreads VMs across fault/update domains in one datacenter. Availability Zones spread across physically separate datacenters in a region. VMSS manages identical VMs and can itself be zone-redundant with autoscaling.
Load Balancer vs App Gateway vs Front Door
Load Balancer is regional L4. Application Gateway is regional L7 with WAF and path routing. Front Door is global L7 with anycast, edge caching and WAF.
Azure SQL vs Cosmos DB
Azure SQL is managed relational with ACID and SQL. Cosmos DB is globally distributed NoSQL with tunable consistency and single-digit-ms latency; pick it for global scale and key-value/document access.
Service Bus vs Event Grid vs Event Hubs
Service Bus is reliable enterprise messaging (queues/topics). Event Grid is reactive pub/sub event routing. Event Hubs is high-throughput streaming/telemetry ingestion.
Private Endpoint vs Service Endpoint
Service Endpoint extends the VNet identity to a PaaS service over the backbone but the service keeps a public IP. Private Endpoint gives the PaaS service a private IP inside your VNet, fully removing public exposure.
How do you make an app highly available on Azure?
Spread across Availability Zones, VMSS or AKS behind a load balancer, zone-redundant or geo-replicated databases, health probes with automatic failover, and stateless tiers with a shared session store.
