Compute Engine + Managed Instance Groups

Compute that grows and heals itself

Compute Engine provides configurable VMs. A Managed Instance Group (MIG) runs identical VMs from an instance template, autoscales them, spreads them across zones, and auto-heals failed instances via health checks.

  • VM — machine types (e2, n2, c3), custom sizes, persistent disks; secured by firewall rules and service accounts.
  • Instance template defines how VMs are built; the MIG holds target size.
  • Autoscaler reacts to CPU / load-balancing utilization / custom metrics.
  • Auto-healing recreates VMs that fail an application health check.
  • Regional MIGs spread across zones; front with the global HTTP(S) Load Balancer for HA.
REFERENCE CARDgcloud
# Instance template + regional managed instance group
gcloud compute instance-templates create web-tpl \
  --machine-type e2-medium --image-family debian-12 --image-project debian-cloud
gcloud compute instance-groups managed create web-mig \
  --template web-tpl --size 2 --region us-central1
# Autoscale 2 -> 8 at 60% CPU
gcloud compute instance-groups managed set-autoscaling web-mig \
  --region us-central1 --min-num-replicas 2 --max-num-replicas 8 \
  --target-cpu-utilization 0.6
Architecture
flowchart LR
    U["Users"] --> LB["HTTP(S) Load Balancer - global"]
    subgraph MIG["Regional MIG  (min 2 / max 8)"]
      direction TB
      V1["VM - zone a"]
      V2["VM - zone b"]
      V3["VM - scaled out"]
    end
    LB --> V1
    LB --> V2
    LB --> V3
    MON["Autoscaler - CPU 60%"] --> MIG
STAR interview answer
S
SituationA media web tier ran on a fixed set of Compute Engine VMs. Traffic spikes saturated CPU and caused errors, and scaling by hand was too slow.
T
TaskMake the tier elastic and self-healing so it absorbs surges automatically without paying for peak all day.
A
ActionI built an instance template with a custom image, created a regional MIG across zones, and configured the autoscaler from 2 to 8 replicas at 60% CPU. Auto-healing recreated any VM that failed the health check, and I fronted the group with the global HTTP(S) Load Balancer, codifying everything in Terraform.
R
ResultThe tier absorbed spikes with no manual action, errors disappeared, failed VMs self-healed across zones, and scaling in off-peak cut steady-state cost by about a third.
02

VPC + Networking

A global network with regional subnets

A GCP VPC is a global resource; its subnets are regional. You control IP ranges, routes and firewall rules, and Cloud NAT provides outbound access for private instances.

  • VPC is global; subnets are regional — a key GCP distinction.
  • Firewall rules are stateful, applied by network tags or service accounts.
  • Cloud NAT gives private VMs outbound internet with no external IP.
  • Cloud Router + routes steer traffic; VPC Peering / Shared VPC connect projects.
  • Private Google Access and Private Service Connect reach Google APIs/services privately.
  • Cloud VPN / Interconnect connect on-prem.
REFERENCE CARDgcloud
# Custom-mode VPC + regional subnet
gcloud compute networks create vpc --subnet-mode custom
gcloud compute networks subnets create app \
  --network vpc --range 10.0.1.0/24 --region us-central1
# Firewall rule (by tag) + Cloud NAT for private egress
gcloud compute firewall-rules create allow-http \
  --network vpc --allow tcp:80 --target-tags web
gcloud compute routers create rtr --network vpc --region us-central1
gcloud compute routers nats create nat --router rtr \
  --region us-central1 --auto-allocate-nat-external-ips \
  --nat-all-subnet-ip-ranges
Architecture
flowchart LR
    NET["Internet"] --> LB["HTTP(S) LB"]
    LB --> APP["App subnet - private"]
    APP --> DB["Data subnet - private"]
    APP --> NAT["Cloud NAT"] --> NET
    APP -. private access .-> API["Google APIs / Cloud SQL"]
STAR interview answer
S
SituationA project had VMs with external IPs on a default network and reached Google services over the public internet. A review flagged the exposure and lack of segmentation.
T
TaskRe-architect into a secure custom VPC enforcing least privilege and passing the review.
A
ActionI created a custom-mode VPC with separate regional subnets for app and data, removed external IPs and added Cloud NAT for controlled egress, wrote tag- and service-account-scoped firewall rules for tier-to-tier traffic only, enabled Private Google Access plus Private Service Connect for Cloud SQL, and turned on VPC Flow Logs.
R
ResultInstances lost their public exposure, service traffic stayed on Google's backbone, the review passed, and Flow Logs gave us the network visibility we'd been missing.
03

Cloud Load Balancing + API Gateway

The front door for traffic and APIs

Cloud Load Balancing offers a global, anycast HTTP(S) load balancer (plus TCP/UDP and internal options). API Gateway (and Apigee for enterprise) is a managed front door for APIs with auth, keys and quotas.

  • Global external HTTP(S) LB — one anycast IP worldwide, content-based routing via URL maps, managed TLS.
  • Network / Internal LB for L4 TCP/UDP and internal traffic.
  • Cloud Armor adds WAF and DDoS protection at the edge.
  • API Gateway — managed gateway for serverless/backends with API keys and JWT auth.
  • Apigee — full API management with quotas, monetization and analytics.
REFERENCE CARDgcloud
# Enable CDN on a backend + build a global URL map (abridged)
gcloud compute backend-services create web-be --global \
  --protocol HTTP --enable-cdn
gcloud compute url-maps create web-map --default-service web-be
gcloud compute target-http-proxies create web-proxy --url-map web-map
gcloud compute forwarding-rules create web-fr --global \
  --target-http-proxy web-proxy --ports 80
# API Gateway from an OpenAPI spec
gcloud api-gateway apis create orders-api
gcloud api-gateway gateways create orders-gw --api orders-api \
  --api-config cfg1 --location us-central1
Architecture
flowchart LR
    U["Users"] --> LB["Global HTTP(S) LB + Cloud Armor"]
    LB --> B1["Backend - /cart"]
    LB --> B2["Backend - /orders"]
    C["API clients"] --> AGW["API Gateway - keys, JWT"]
    AGW --> RUN["Cloud Run / Functions"]
STAR interview answer
S
SituationWe were moving to microservices on GKE and needed global path-based routing plus a secured public API with quotas.
T
TaskRoute traffic to the right service worldwide and expose a protected, rate-limited API.
A
ActionI used the global external HTTP(S) load balancer with URL maps for path/host routing and a Google-managed TLS certificate, added Cloud Armor for WAF and rate limiting, and put serverless backends behind API Gateway with API keys and JWT auth for external consumers.
R
ResultA single anycast IP served users globally with low latency, Cloud Armor blocked common attacks and abusive clients, and the API gateway enforced keys and quotas cleanly at the edge.
04

Cloud CDN + Cloud DNS

Global delivery and smart DNS

Cloud CDN caches content at Google's edge to cut latency, riding on the HTTP(S) load balancer. Cloud DNS is a scalable, 100% SLA authoritative DNS service with routing policies and health checks.

  • Cloud CDN — enabled on a backend service; caches static/dynamic content at the edge.
  • Cloud DNS — public and private zones, low-latency anycast resolution.
  • Routing policies — weighted round-robin and geolocation; health checks for failover.
  • The global LB anycast IP plus Cloud DNS gives users the nearest healthy entry point.
  • Use signed URLs/cookies to protect cached private content.
REFERENCE CARDgcloud
# Enable Cloud CDN on the backend
gcloud compute backend-services update web-be --global --enable-cdn
# Managed DNS zone + record
gcloud dns managed-zones create web-zone --dns-name example.com. \
  --description 'public zone'
gcloud dns record-sets create www.example.com. --zone web-zone \
  --type A --ttl 300 --rrdatas <lb-ip>
Architecture
flowchart LR
    U["Users - global"] --> DNS["Cloud DNS - geo / weighted"]
    DNS --> CDN["Cloud CDN edge (on the LB)"]
    CDN --> O1["Backend - region A"]
    DNS -. failover .-> O2["Backend - region B"]
STAR interview answer
S
SituationA global site served assets from one region, so distant users saw slow loads and a regional issue risked downtime.
T
TaskCut global latency and add DNS-level failover across regions.
A
ActionI enabled Cloud CDN on the load balancer's backend so static assets cached at the edge, fronted everything with the global anycast IP, and used Cloud DNS with health checks and a failover/geolocation policy across two regional backends.
R
ResultPage-load latency dropped for international users as the edge served most requests, origin load fell, and DNS-level failover kept the site available during a later regional incident.
05

Cloud SQL + Firestore

Pick the right database for the job

Cloud SQL is a managed relational service (MySQL, PostgreSQL, SQL Server) with HA and automated backups. Firestore is a serverless, autoscaling NoSQL document database; Bigtable and Spanner cover wide-column and global-relational needs.

  • Cloud SQL — regional HA (synchronous standby), read replicas, automated backups + PITR.
  • Firestore — serverless document DB, real-time listeners, strong consistency, autoscaling.
  • Spanner — globally distributed, strongly consistent relational at scale.
  • Bigtable — low-latency wide-column for huge analytical/time-series workloads.
  • Choose relational (Cloud SQL/Spanner) for joins/ACID; Firestore/Bigtable for scale-out NoSQL.
REFERENCE CARDgcloud
# Cloud SQL (PostgreSQL) with HA
gcloud sql instances create appdb --database-version POSTGRES_15 \
  --tier db-custom-2-7680 --region us-central1 --availability-type REGIONAL
gcloud sql databases create app --instance appdb
# Firestore in Native mode
gcloud firestore databases create --location nam5
Architecture
flowchart LR
    APP["Application"] --> CSQL["Cloud SQL - primary (HA)"]
    CSQL -. sync .-> STB["Standby - zone b"]
    CSQL --> RR["Read replica - reporting"]
    APP --> FS["Firestore"]
    FS --> C1["Collections - autoscale"]
STAR interview answer
S
SituationReporting queries were overloading the primary Cloud SQL instance and slowing transactions, and a session/cart store on the same database struggled during spikes.
T
TaskProtect transactional performance and give the cart a scalable, low-latency store.
A
ActionI switched Cloud SQL to a regional HA configuration for automatic failover, added a read replica and pointed reporting at it, tuned automated backups with point-in-time recovery, and moved sessions and cart data to Firestore with a deliberate document/collection model. Access went through the Cloud SQL Auth proxy and private IP.
R
ResultTransaction latency recovered, failover tested cleanly, the cart scaled through spikes at low latency, and moving reads to the replica removed the reporting bottleneck.

Cloud Functions + Cloud Run

Run code, not servers

Cloud Functions runs small event-driven functions with no servers to manage. Cloud Run runs containerized services serverlessly. Both autoscale (including to zero) and bill per use.

  • Cloud Functions (2nd gen) — HTTP or event triggers (Cloud Storage, Pub/Sub, Firestore, Eventarc).
  • Cloud Run — any container, request- or CPU-based autoscaling, scale to zero, concurrency control.
  • Both bill only for what you use and scale automatically.
  • Secure with per-service service accounts, Secret Manager and VPC connectors.
  • Mind cold starts — set minimum instances on latency-sensitive services.
REFERENCE CARDgcloud
# Cloud Functions (2nd gen), HTTP trigger
gcloud functions deploy hello --gen2 --runtime python312 \
  --region us-central1 --trigger-http --entry-point main
# Cloud Run service from a container image
gcloud run deploy orders --image gcr.io/proj/orders \
  --region us-central1 --min-instances 1 --allow-unauthenticated
Architecture
flowchart LR
    GCS["Cloud Storage event"] --> FN["Cloud Function / Cloud Run"]
    HTTP["HTTP trigger"] --> FN
    PS["Pub/Sub / Eventarc"] --> FN
    FN --> FS["Firestore"]
    FN --> OUT["Storage / Pub/Sub"]
    FN -. failures .-> DLQ["Dead-letter topic"]
STAR interview answer
S
SituationAn image pipeline ran on always-on GKE workers that were idle most of the day but overwhelmed during upload bursts.
T
TaskReplace it with something that scales to zero and still handles bursts.
A
ActionI triggered a Cloud Function on Cloud Storage object-finalize events to process the image and write metadata to Firestore, used a dedicated service account and Secret Manager for credentials, added a dead-letter topic with retries, and moved the heavier transform to Cloud Run with a minimum instance to avoid cold starts.
R
ResultCompute cost fell sharply since we paid per request, bursts were absorbed automatically, and we removed all cluster and server maintenance overhead.

Pub/Sub — Event-Driven

Decouple, buffer, and fan out

Cloud Pub/Sub is a globally available messaging service that decouples producers and consumers. A topic fans a message out to many subscriptions, each consumed independently with at-least-once (or exactly-once) delivery.

  • Topic → subscriptions — one publish fans out to many subscribers.
  • Pull or push delivery; push can target Cloud Run/Functions endpoints.
  • At-least-once by default; exactly-once and ordering keys available.
  • Dead-letter topics and retry policies for poison messages.
  • Global by design — publishers and subscribers can be in different regions.
REFERENCE CARDgcloud
# Topic + subscription with a dead-letter policy
gcloud pubsub topics create order-events
gcloud pubsub topics create order-dlq
gcloud pubsub subscriptions create inventory-sub \
  --topic order-events --ack-deadline 30 \
  --dead-letter-topic order-dlq --max-delivery-attempts 5
Architecture
flowchart LR
    SRC["Order service"] --> TOP["Pub/Sub topic - order-events"]
    TOP --> S1["Sub - inventory"] --> W1["Worker"]
    TOP --> S2["Sub - notifications"] --> W2["Email / SMS"]
    TOP --> S3["Sub - analytics"] --> W3["BigQuery consumer"]
    S1 -. poison .-> DLQ["Dead-letter topic"]
STAR interview answer
S
SituationAn order service called inventory, notifications and analytics synchronously, so one slow downstream failed the whole checkout.
T
TaskDecouple the flow so orders are accepted instantly and downstreams process independently and reliably.
A
ActionOn each order I published to a Pub/Sub topic and created separate subscriptions for inventory, notifications and analytics, each with its own consumer. I used ordering keys where sequence mattered, tuned the ack deadline, enabled a dead-letter topic with a retry policy, and streamed the analytics subscription into BigQuery.
R
ResultCheckout became instant and resilient — a downstream outage no longer failed orders because messages buffered and retried — and new consumers were added later with no change to the producer.

Cloud Monitoring + Cloud Logging

See it, alert on it, audit it

Google Cloud's operations suite: Cloud Monitoring for metrics, dashboards and alerting; Cloud Logging for centralized logs; and Cloud Audit Logs for an immutable record of who did what.

  • Cloud Monitoring — metrics, dashboards, uptime checks, alerting policies to many channels.
  • Cloud Logging — centralized logs; query with the Logs Explorer; export via sinks.
  • Log-based metrics turn log patterns into alertable metrics.
  • Cloud Audit Logs — Admin Activity and Data Access logs for governance and compliance.
  • Cloud Trace / Profiler add latency tracing and CPU/heap profiling.
REFERENCE CARDgcloud
# Notification channel + alerting policy (from files)
gcloud beta monitoring channels create --channel-content-from-file chan.json
gcloud alpha monitoring policies create --policy-from-file cpu-policy.json
# Export audit/app logs to BigQuery via a sink
gcloud logging sinks create audit-bq \
  bigquery.googleapis.com/projects/proj/datasets/audit \
  --log-filter='logName:cloudaudit.googleapis.com'
Architecture
flowchart LR
    RES["GCE / GKE / Cloud SQL / Run"] --> MON["Cloud Monitoring - metrics"]
    RES --> LOG["Cloud Logging"]
    MON --> AL["Alerting policy - CPU / 5xx / latency"]
    AL --> CH["Channel"] --> N["Slack / PagerDuty / Email"]
    RES --> AUD["Cloud Audit Logs"] --> BQ["BigQuery / sink - retention"]
STAR interview answer
S
SituationIncidents were being spotted by users first, and there was no consolidated record of administrative actions across projects.
T
TaskBuild proactive monitoring and alerting plus a compliance-grade audit trail.
A
ActionI built Cloud Monitoring dashboards and uptime checks, created alerting policies on CPU, 5xx and latency wired to Slack and PagerDuty channels, centralized logs in Cloud Logging with log-based metrics for key error patterns, added Cloud Trace for latency, and exported Cloud Audit Logs to BigQuery through a sink for long-term retention and querying.
R
ResultMean time to detect and recover dropped sharply, we caught issues before customers, and the exported audit logs satisfied compliance and made post-incident RCA straightforward.

High-yield Q&A

What is global vs regional vs zonal in GCP?
VPC networks and the external HTTP(S) load balancer are global. Subnets, regional MIGs and Cloud SQL are regional. Individual VMs and zonal MIGs live in a single zone. This scope model underpins most GCP design answers.
Firewall rules vs Security Groups (AWS)
GCP firewall rules are stateful, defined at the VPC level, and applied to instances by network tags or service accounts rather than attached objects like AWS security groups.
Cloud SQL vs Spanner vs Firestore
Cloud SQL is managed regional relational. Spanner is globally distributed, strongly consistent relational at scale. Firestore is serverless NoSQL document with real-time sync. Pick by scale, consistency and data model.
Cloud Functions vs Cloud Run
Functions run small event-driven code with managed runtimes. Cloud Run runs any container with more control over concurrency, CPU and dependencies. Both scale to zero and bill per use.
Pub/Sub vs a queue like SQS
Pub/Sub is topic-based pub/sub that fans out to many subscriptions and is global by design, with at-least-once (optionally exactly-once) delivery and dead-letter topics; it covers both fan-out and buffered-queue patterns.
Private Google Access vs Private Service Connect
Private Google Access lets instances without external IPs reach Google APIs via internal routing. Private Service Connect exposes services (Google or your own) through private endpoints inside your VPC.
How do you make an app highly available on GCP?
Use regional MIGs or GKE across zones behind the global load balancer, regional/HA databases or Spanner, health checks with auto-healing and failover, and stateless tiers with a shared session store.
