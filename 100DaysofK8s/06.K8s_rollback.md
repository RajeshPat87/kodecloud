The rollout history is visible right in your `kubectl get all` output — two replicasets exist: `6c744d9dd6` (current, 3 pods) and `fc677cbc9` (previous, 0 pods). Rollback will swap them.

## Step 1 — Check rollout history

```bash
kubectl rollout history deployment/nginx-deployment
```

Shows the revision numbers and change causes.

## Step 2 — Rollback to previous revision

```bash
kubectl rollout undo deployment/nginx-deployment
```

## Step 3 — Monitor

```bash
kubectl rollout status deployment/nginx-deployment
kubectl get pods
kubectl get replicaset
```

Expected after rollback:
```
deployment "nginx-deployment" successfully rolled out

NAME                                          DESIRED   CURRENT   READY
replicaset.apps/nginx-deployment-fc677cbc9    3         3         3
replicaset.apps/nginx-deployment-6c744d9dd6   0         0         0
```

The old replicaset `fc677cbc9` scales back to 3, and `6c744d9dd6` (the buggy release) drops to 0.

## Step 4 — Confirm previous image is restored

```bash
kubectl describe deployment nginx-deployment | grep Image
```

## Requirement trace

| Requirement | Evidence |
|---|---|
| Rollback `nginx-deployment` to previous revision | `kubectl rollout undo deployment/nginx-deployment` |
| Previous replicaset restored | `fc677cbc9` back to 3 replicas |
| All pods operational | 3/3 Running on old replicaset |

One command does it — `kubectl rollout undo` is the production-correct way to revert because it uses Kubernetes' built-in revision history (the old replicaset kept at 0 replicas is exactly for this purpose). No manifest editing needed for a rollback.
