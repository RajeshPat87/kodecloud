# Runbook — Kubernetes Rolling Update: `nginx-deployment` to `nginx:1.19`

**Deployment:** `nginx-deployment` · **Replicas:** 3 · **Image:** `nginx:1.19`
**Strategy:** RollingUpdate · **Selector:** `app: nginx-app`
**Status:** Verified / applied cleanly

## 1. Purpose

Update the existing `nginx-deployment` on the Kubernetes cluster from its current nginx
image to `nginx:1.19` using a declarative rolling update strategy. All 3 pods must remain
operational during and after the update. No manual imperative commands (`kubectl set image`)
— the manifest is the source of truth.

## 2. Core concept — why rolling update + declarative

**Rolling update** replaces pods incrementally rather than all at once:
- Brings up new pods (`maxSurge`) before killing old ones
- Never takes more than `maxUnavailable` pods down at once
- Result: zero downtime during the image change

**Declarative (`kubectl apply`) over imperative (`kubectl set image`):**
- Manifest lives in Git — reproducible, auditable, reviewable
- CI/CD pipeline applies it — no manual intervention
- Kubernetes reconciles cluster state to match the manifest
- Rollback = revert the Git commit and re-apply

**Selector immutability** — `spec.selector.matchLabels` is immutable once a deployment
is created. You cannot change it. The manifest you apply must carry the **same selector**
the deployment was created with, or `kubectl apply` rejects it with
`field is immutable`. Always check the existing selector before applying.

## 4. Pre-flight checks

Always run before touching an existing deployment:

```bash
# current state — replicas, image, selector
kubectl get deployment nginx-deployment -o yaml | grep -E "image:|replicas:|selector:" -A3

# exact selector (immutable — must match your manifest)
kubectl get deployment nginx-deployment -o jsonpath='{.spec.selector.matchLabels}'

# current pods
kubectl get pods -l app=nginx-app

# current image
kubectl describe deployment nginx-deployment | grep Image
```

## 5. Rolling update manifest

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx-app
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 1
  template:
    metadata:
      labels:
        app: nginx-app
    spec:
      containers:
        - name: nginx
          image: nginx:1.19
EOF
```

**`maxSurge: 1`** — one extra pod allowed during the update (4 pods temporarily).
**`maxUnavailable: 1`** — one pod allowed down at a time (minimum 2 always running).
Result: Kubernetes replaces pods one at a time, keeping at least 2 of 3 serving traffic.

## 6. Monitor the rollout

```bash
# blocks until complete (or times out)
kubectl rollout status deployment/nginx-deployment

# watch pods cycling
kubectl get pods -w

# confirm new image
kubectl describe deployment nginx-deployment | grep Image

# confirm new replicaset created
kubectl get replicaset
```

Expected output:
```
deployment "nginx-deployment" successfully rolled out

NAME                                READY   STATUS    RESTARTS   AGE
nginx-deployment-<newhash>-xxxxx    1/1     Running   0          ...
nginx-deployment-<newhash>-xxxxx    1/1     Running   0          ...
nginx-deployment-<newhash>-xxxxx    1/1     Running   0          ...

Image: nginx:1.19
```

A new replicaset hash replaces the old one (`fc677cbc9`). The old replicaset is kept
at 0 replicas for rollback history.

## 7. Rollback

If the new image has issues, roll back to the previous version instantly:

```bash
kubectl rollout undo deployment/nginx-deployment
kubectl rollout status deployment/nginx-deployment
kubectl describe deployment nginx-deployment | grep Image
```

The old replicaset scales back up, new one scales to 0.
Check rollout history:
```bash
kubectl rollout history deployment/nginx-deployment
```

## 8. Production CI/CD pattern

In production, this manifest lives in Git and the pipeline applies it:

```bash
# pipeline script (Jenkins/GitHub Actions)
kubectl apply -f k8s/nginx-deployment.yaml
kubectl rollout status deployment/nginx-deployment --timeout=120s
if [ $? -ne 0 ]; then
  echo "Rollout failed — initiating rollback"
  kubectl rollout undo deployment/nginx-deployment
  exit 1
fi
echo "Rollout successful — nginx:1.19 deployed"
```

**Flow:**
```
Update image tag in YAML → Git commit → PR review → Merge
         ↓
CI/CD: kubectl apply -f nginx-deployment.yaml
         ↓
kubectl rollout status (blocks, confirms success)
         ↓
Auto-rollback on failure
```

## 10. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `spec.selector: field is immutable` | manifest selector doesn't match existing | check `kubectl get deployment ... -o jsonpath='{.spec.selector.matchLabels}'` and match it exactly in both `selector.matchLabels` and `template.metadata.labels` |
| Pods stuck in `Pending` | resource constraints or node capacity | `kubectl describe pod <pod>` → check Events section |
| Pods `ImagePullBackOff` | wrong image tag or registry unreachable | verify `nginx:1.19` is accessible; check `kubectl describe pod` |
| Rollout hangs | `maxUnavailable: 0` + `maxSurge: 0` (invalid) | ensure at least one of them is > 0 |
| Old pods not terminating | `maxUnavailable: 0` too conservative | increase `maxUnavailable` or reduce `replicas` |
| `rollout status` times out | pods not becoming Ready | check resource limits, liveness probes, image issues |

## 11. Key lesson — always check selector first

The `spec.selector` field is immutable. Before applying any update to an existing
deployment, **always run**:
```bash
kubectl get deployment <name> -o jsonpath='{.spec.selector.matchLabels}'
```
and match it exactly in your manifest. This is the single most common error when
updating existing deployments declaratively.
