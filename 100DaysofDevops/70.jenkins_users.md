## Title

Grant Read-Only Job Access to User `rose` with Project-based Matrix Authorization (Jenkins)

***

## Context

The Nautilus team is configuring Jenkins to use **Project-based Matrix Authorization Strategy**. They’ve:

- Created a Jenkins user `rose` (password `TmPcZjtRQx`, full name `Rose`).
- Enabled matrix authorization globally, granting `rose` **Overall → Read** and removing all rights from Anonymous while keeping `admin` as full administrator.

The remaining requirement is:

> For the existing job, grant **rose** user only **read** permissions, disregarding other permissions such as Agent, SCM etc.

This is done via **project-based security** on the job’s configuration.

***

## Prerequisites

Before applying job-level permissions:

1. User `rose` exists:

   - Created via **Manage Jenkins → Users → Create User**:
     - Username: `rose`.
     - Password: `TmPcZjtRQx`.
     - Full name: `Rose`.

2. Global authorization is set to **Project-based Matrix Authorization Strategy** (or equivalent), with:

   - `admin`: Overall → Administer (and typically full permissions).
   - `rose`: Overall → Read.
   - `Anonymous`: no permissions.

***

## Procedure: Job-Level Project-based Security for `rose`

### Step 1: Open the existing job

1. Log in to Jenkins as `admin` / `Adm!n321`.
2. From the Jenkins dashboard, click the name of the existing job (e.g., `shareddevops`, `job1`, etc.).

### Step 2: Go to job configuration

1. On the job page, click **Configure** in the left sidebar.

### Step 3: Enable project-based security for this job

1. Scroll down until you find the **Security** or **Authorization** section.
2. Look for a checkbox such as:

   - **Enable project-based security**
   - **Project-based Matrix Authorization Strategy** (wording depends on Jenkins version).

3. Check **Enable project-based security**.

Once enabled, Jenkins displays a **matrix table** for this job with rows for users/groups and columns for permission categories (Overall, Job, Run, View, Agent, SCM, etc.).

***

### Step 4: Add `admin` and `rose` to the job’s matrix

1. In the job’s matrix section:

   - Click **Add user or group**.
   - Add `admin`.
   - Add `rose`.

You should now see at least two rows:

- `admin`
- `rose`

***

### Step 5: Set job permissions for `admin`

1. For the `admin` row, grant full job-level permissions, for example:

   - **Job**:
     - Read
     - Configure
     - Build
     - Cancel
     - Delete
   - Other categories (Run, View, Agent, SCM, etc.) as needed.

This ensures the `admin` user retains full control over the job.

***

### Step 6: Set job permissions for `rose` — **Read-only**

Requirement states: *grant `rose` user only read permissions, disregarding other permissions such as Agent, SCM etc.*

1. For the `rose` row, **check only**:

   - **Job → Read**

2. Ensure **all other permissions** for `rose` remain **unchecked**:

   - Do **not** check:
     - Job → Configure, Build, Delete, Cancel.
     - Any permissions under Agent, SCM, Run, View, or other categories.

This configuration gives `rose` **view-only access** to the job (read its configuration and status) without the ability to modify or trigger builds.

***

### Step 7: Save job configuration

1. Scroll down to the bottom of the job configuration page.
2. Click **Save**.

The job now enforces project-based matrix authorization, with `rose` having **read-only** rights and `admin` having full control.
