# Runbook — Chained Jenkins Builds: Deploy → Restart httpd

**Jobs:** `xfusion-app-deployment` (upstream) → `manage-services` (downstream)
**Target:** App Server 1 (`stapp01`) · **Deploy dir:** `/var/www/html` · **All setup via CLI**

## 1. Core concept — why chained builds

The requirement is: *restart Apache only if the deployment succeeded.* That "only if" is the whole point, and it maps to a Jenkins feature called **upstream/downstream chaining**.

**The relationship.** One job (upstream) finishes and automatically triggers another (downstream). Here `xfusion-app-deployment` is upstream, `manage-services` is downstream. You never run `manage-services` by hand — it fires as a consequence of a deployment.

**The conditional gate — build stability.** Every Jenkins build ends in a status:
- **SUCCESS** (stable, blue/green) — all steps exited 0
- **UNSTABLE** (yellow) — passed but flagged (e.g. failing tests)
- **FAILURE** (red) — a step exited non-zero

The chain is configured with a **threshold**: "trigger downstream only if upstream is **stable** (SUCCESS)." So if `git pull` fails — network down, merge conflict, auth error — the deployment build goes red, the threshold isn't met, and `manage-services` **never runs**. Apache is only restarted when there's actually a good deployment to serve. That's exactly the safety the DevOps team asked for: no restart on a broken deploy.

**Why two jobs instead of one script.** You could `git pull && systemctl restart httpd` in a single job. The team chose chaining deliberately because:
- **Separation of concerns** — deployment and service management are independent, reusable units. `manage-services` can later be triggered by *other* deploy jobs too (the task hints at "all app servers").
- **Independent visibility** — you see at a glance whether the *deploy* failed or the *restart* failed; they're separate build histories.
- **Composability** — chains scale. One deploy can fan out to restart httpd on stapp01, stapp02, stapp03 as parallel downstreams.

**Where the link is stored.** The trigger lives in the **upstream** job's *post-build action* ("Build other projects" → `manage-services` → "trigger only if stable"). In `config.xml` that's the `<publishers><hudson.tasks.BuildTrigger>` block with `<threshold><name>SUCCESS</name>`. Jenkins reads it as a directed edge in its dependency graph. (You can define the same edge from the downstream side via "Build after other projects are built" — same graph, opposite entry point. Define it once, not both.)

**Idempotency (Note 2).** Both jobs must survive repeated runs. `git pull` on an up-to-date repo returns "Already up to date" (exit 0); `systemctl restart httpd` restarts cleanly every time. So re-running the chain always ends stable → downstream always fires → always green.

### 6.3 Upstream job `xfusion-app-deployment` (with the chain built in)
```bash
cat <<'EOF' | java -jar jenkins-cli.jar -s "$JENKINS_URL" -auth admin:'Adm!n321' \
  create-job xfusion-app-deployment
<project>
  <description>Pull master into /var/www/html on App Server 1</description>
  <scm class="hudson.scm.NullSCM"/>
  <assignedNode>stapp01</assignedNode>
  <canRoam>false</canRoam>
  <disabled>false</disabled>
  <triggers/>
  <concurrentBuild>false</concurrentBuild>
  <builders>
    <hudson.tasks.Shell>
      <command>sudo git config --global --add safe.directory /var/www/html
cd /var/www/html
sudo git checkout master
sudo git pull origin master</command>
    </hudson.tasks.Shell>
  </builders>
  <publishers>
    <hudson.tasks.BuildTrigger>
      <childProjects>manage-services</childProjects>
      <threshold>
        <name>SUCCESS</name>
        <ordinal>0</ordinal>
        <color>BLUE</color>
        <completeBuild>true</completeBuild>
      </threshold>
    </hudson.tasks.BuildTrigger>
  </publishers>
  <buildWrappers/>
</project>
EOF
```
The `BuildTrigger` publisher with `<threshold><name>SUCCESS</name>` **is** the "trigger downstream only if stable" gate (concept, section 1).

### 6.4 Downstream job `manage-services`
```bash
cat <<'EOF' | java -jar jenkins-cli.jar -s "$JENKINS_URL" -auth admin:'Adm!n321' \
  create-job manage-services
<project>
  <description>Restart httpd (downstream of xfusion-app-deployment)</description>
  <scm class="hudson.scm.NullSCM"/>
  <assignedNode>stapp01</assignedNode>
  <canRoam>false</canRoam>
  <disabled>false</disabled>
  <triggers/>
  <concurrentBuild>false</concurrentBuild>
  <builders>
    <hudson.tasks.Shell>
      <command>sudo systemctl restart httpd
sudo systemctl is-active httpd</command>
    </hudson.tasks.Shell>
  </builders>
  <publishers/>
  <buildWrappers/>
</project>
EOF
```

|---|---|

| Job `manage-services` restarts httpd | `systemctl restart httpd` step |

| Passes repetitive runs (Note 2) | idempotent `git pull` + `restart`; 2× green |

## 9. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Downstream never runs | Missing/incorrect `BuildTrigger`, or threshold not SUCCESS | verify `get-job xfusion-app-deployment` shows the publisher with SUCCESS |
| Downstream runs even on failure | threshold too permissive | ensure `<name>SUCCESS</name>`, not FAILURE/UNSTABLE |
| `git pull` prompts for auth | doc-root remote lacks creds | `sudo git -C /var/www/html remote set-url origin http://sarah:Sarah_pass123@gitea:3000/sarah/web.git` |
| `fatal: dubious ownership` | doc root not sarah-owned | `safe.directory` lines (section 5) |
| `sudo: password required` in build | NOPASSWD sudoers missing | recreate `/etc/sudoers.d/sarah` |
| `create-node` XML parse error | ssh-slaves version schema mismatch | `get-node` a UI-made node, reuse its XML |
| `create-job` fails, job exists | duplicate | `delete-job <name>` then re-create, or `update-job <name> < config.xml` |
| chain wired twice | trigger on both jobs | keep it only in upstream `publishers` |
