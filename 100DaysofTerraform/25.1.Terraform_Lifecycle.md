# Terraform Lifecycle Meta-Argument — Complete Guide

## What is `lifecycle`?

`lifecycle` is a **meta-argument** available on every Terraform resource block. It tells Terraform **how to behave** during create/update/destroy operations — overriding the default behavior. It lives inside the resource block but is managed by Terraform itself, not the provider.

```hcl
resource "aws_instance" "example" {
  ami           = "ami-0c101f26f147fa7fd"
  instance_type = "t2.micro"

  lifecycle {
    # one or more lifecycle rules here
    create_before_destroy = true
    prevent_destroy       = true
    ignore_changes        = [tags]
    replace_triggered_by  = [aws_key_pair.example.id]
  }
}
```

---

## The five lifecycle arguments

| Argument | Type | Default | Purpose |
|---|---|---|---|
| `create_before_destroy` | bool | `false` | New resource before old is deleted |
| `prevent_destroy` | bool | `false` | Block any destruction |
| `ignore_changes` | list | `[]` | Ignore drift on specific attributes |
| `replace_triggered_by` | list | `[]` | Force replace when another resource changes |
| `precondition` / `postcondition` | block | none | Validate before/after apply |

---

## 1. `create_before_destroy`

### What it does
Reverses the default destroy-then-create order for `-/+` replacements. New resource is created and verified **before** the old one is destroyed.

### Default behavior (without it)
```
Old resource DESTROYED → [GAP = DOWNTIME] → New resource CREATED
```

### With `create_before_destroy = true`
```
New resource CREATED → [BOTH EXIST BRIEFLY] → Old resource DESTROYED
```

### Example

```hcl
resource "aws_instance" "web" {
  ami           = "ami-0abcdef1234567890"   # changed AMI → forces -/+
  instance_type = "t2.micro"

  lifecycle {
    create_before_destroy = true
  }

  tags = { Name = "web-server" }
}
```

### Plan output
```hcl
-/+ resource "aws_instance" "web" {
      ~ id  = "i-old123" -> (known after apply)
      ~ ami = "ami-old" -> "ami-new"          # forces replacement
    }
Plan: 1 to add, 0 to change, 1 to destroy.
```

### Behind the scenes (step by step)
```
Step 1: terraform apply starts
Step 2: RunInstances(ami-new) → i-new456 created
Step 3: Terraform polls until i-new456 is "running"
Step 4: TerminateInstances(i-old123) → old destroyed
Step 5: terraform.tfstate updated with i-new456
```

### Availability timeline
```
Without lifecycle:
Time →  [old RUNNING] → [old STOPPED] → [GAP] → [new RUNNING]
                                          ↑ downtime

With create_before_destroy:
Time →  [old RUNNING] → [old+new RUNNING] → [old STOPPED] → [new RUNNING]
                              ↑ zero downtime, brief double-cost
```

### When to use
- AMI replacements on production instances
- Certificate rotations
- Any ForceNew attribute change where availability matters
- Behind a load balancer (detach old → new ready → attach new → terminate old)

### Watch-outs
- **Double cost** during the overlap period (both instances running)
- **Name tag conflict** — if old and new try to register the same Name tag
- **Dependency ordering** — if another resource depends on this one, Terraform must update that dependency too during the swap
- **Doesn't prevent downtime** if the resource type can't have two instances simultaneously (e.g. unique constraint on a name)

## 2. `prevent_destroy`

### What it does
Places a **hard guard** that makes Terraform error if anything tries to destroy the resource — whether from `terraform destroy`, a `-/+` replacement, or removing the resource from `main.tf`.

### Example

```hcl
resource "aws_rds_instance" "production_db" {
  identifier     = "prod-db"
  instance_class = "db.t3.medium"
  engine         = "mysql"

  lifecycle {
    prevent_destroy = true      # cannot be destroyed by terraform
  }
}
```

### Behind the scenes
```
terraform destroy →
  Error: Instance cannot be destroyed
  on main.tf line 1, in resource "aws_rds_instance" "production_db":
  lifecycle.prevent_destroy is true

terraform apply (after removing resource from main.tf) →
  Same error — Terraform won't remove it from the real infra
```

### Plan output when triggered
```
╷
│ Error: Instance cannot be destroyed
│
│   on main.tf line 6, in resource "aws_rds_instance" "production_db":
│    6:     prevent_destroy = true
│
│ This resource is protected from destruction.
╵
```

### How to override it (when you genuinely need to destroy)
```hcl
# Step 1: remove prevent_destroy
lifecycle {
  prevent_destroy = false   # or remove the lifecycle block entirely
}

# Step 2: apply the config change (updates the lifecycle, no AWS change)
terraform apply

# Step 3: now destroy works
terraform destroy
```

### When to use
- Production databases (`aws_rds_instance`, `aws_dynamodb_table`)
- S3 buckets with critical data
- KMS keys (losing a KMS key = losing encrypted data forever)
- IAM roles tied to production workloads
- Any resource where accidental deletion = data loss or major incident

### Watch-outs
- **Only guards Terraform** — doesn't prevent deletion via AWS Console, CLI, or other tools
- **Must be removed before legitimate destroy** — two-step process (remove flag → apply → destroy)
- **Doesn't protect from `terraform state rm`** — removing from state bypasses the guard (then a subsequent `apply` would try to create it again)
- **CI/CD pipelines** — protect long-lived resources in shared accounts where pipelines run `terraform destroy`

## 3. `ignore_changes`

### What it does
Tells Terraform to **ignore drift** on specific attributes. When Terraform detects a difference between `main.tf` and the real resource state, it normally shows it as a change. `ignore_changes` suppresses that for the listed attributes.

### Example — ignore specific attributes

```hcl
resource "aws_instance" "app" {
  ami           = "ami-0c101f26f147fa7fd"
  instance_type = "t2.micro"

  lifecycle {
    ignore_changes = [
      tags["LastDeployedAt"],    # ignore this specific tag key
      user_data,                 # don't revert user_data changes
      ami,                       # don't force replace when AMI changes externally
    ]
  }
}
```

### Example — ignore ALL changes (`all`)

```hcl
resource "aws_instance" "legacy" {
  ami           = "ami-0c101f26f147fa7fd"
  instance_type = "t2.micro"

  lifecycle {
    ignore_changes = all        # Terraform manages creation only; never updates
  }
}
```

### Behind the scenes
```
External change: Auto Scaling changes instance_type to t2.large
terraform refresh → detects instance_type differs (t2.micro vs t2.large)

Without ignore_changes:
  terraform plan → ~ instance_type = "t2.large" -> "t2.micro"   (would revert it)

With ignore_changes = [instance_type]:
  terraform plan → No changes   (drift suppressed)
```

### Common ignore_changes use cases

| Scenario | What to ignore |
|---|---|
| ASG manages instance count | `ignore_changes = [desired_capacity]` on `aws_autoscaling_group` |
| External tool manages tags | `ignore_changes = [tags]` or specific tag keys |
| AMI baked by CI, Terraform just tracks | `ignore_changes = [ami]` |
| User data runs once at launch | `ignore_changes = [user_data]` |
| RDS auto-manages storage | `ignore_changes = [allocated_storage]` |
| Kubernetes manages node labels | `ignore_changes = [node_config[0].labels]` |

### Tag-specific ignore (Terraform 1.0+)

```hcl
lifecycle {
  ignore_changes = [
    tags["ManagedBy"],          # ignore one tag key
    tags["LastModified"],        # ignore another tag key
    # tags                       # this would ignore ALL tags
  ]
}
```

### Watch-outs
- **`ignore_changes = all`** is a blunt instrument — Terraform creates the resource but never updates it. Use sparingly.
- **Doesn't ignore on first apply** — `ignore_changes` only suppresses drift detection after initial creation. First apply still applies all attributes.
- **Doesn't prevent drift** — the real resource can diverge indefinitely from `main.tf`; Terraform just won't care.
- **Debugging confusion** — future engineers may not understand why Terraform isn't fixing drift. Document why you added `ignore_changes`.

## 4. `replace_triggered_by` (Terraform 1.2+)

### What it does
Forces a **replacement** of a resource when a **different** resource or attribute changes — even if the first resource's own config didn't change. Creates cross-resource replacement dependencies.

### Example

```hcl
resource "aws_key_pair" "devops_kp" {
  key_name   = "devops-kp"
  public_key = tls_private_key.devops.public_key_openssh
}

resource "aws_instance" "devops_ec2" {
  ami           = "ami-0c101f26f147fa7fd"
  instance_type = "t2.micro"
  key_name      = aws_key_pair.devops_kp.key_name

  lifecycle {
    replace_triggered_by = [
      aws_key_pair.devops_kp.id    # if key pair changes → recreate instance too
    ]
  }
}
```

### Behind the scenes
```
Scenario: TLS key regenerated → aws_key_pair.devops_kp gets new ID

Without replace_triggered_by:
  terraform plan → aws_key_pair changes, instance untouched
  Result: instance still has old key embedded → SSH broken

With replace_triggered_by = [aws_key_pair.devops_kp.id]:
  terraform plan → aws_key_pair changes → instance also flagged -/+
  Result: new instance launched with new key pair → SSH works
```

### Plan output
```hcl
-/+ resource "aws_instance" "devops_ec2" {
      ~ id = "i-old" -> (known after apply)
        # replacement triggered by aws_key_pair.devops_kp.id
    }
```

### When to use
- Instance depends on a resource that regenerates (certificates, keys)
- Launch template version changes should replace instances
- Configuration object changes should force re-deploy of consumers
- Any "if X changes, Y must be fully replaced" relationship

## 5. `precondition` and `postcondition` (Terraform 1.2+)

### What it does
**`precondition`** — validates inputs/state **before** Terraform creates or modifies the resource. Apply fails if condition is false.

**`postcondition`** — validates **after** the resource is created/updated. Apply fails and rolls back if condition is false.

### Example — precondition

```hcl
variable "instance_type" {
  default = "t2.micro"
}

resource "aws_instance" "devops_ec2" {
  ami           = "ami-0c101f26f147fa7fd"
  instance_type = var.instance_type

  lifecycle {
    precondition {
      condition     = contains(["t2.nano", "t2.micro", "t2.small"], var.instance_type)
      error_message = "Instance type must be t2.nano, t2.micro, or t2.small. Got: ${var.instance_type}"
    }
  }
}
```

**Behind the scenes:**
```
terraform apply -var="instance_type=t3.xlarge"
→ Error: Instance type must be t2.nano, t2.micro, or t2.small. Got: t3.xlarge
→ Apply stopped BEFORE creating the resource
→ No AWS API call made
```

### Example — postcondition

```hcl
resource "aws_instance" "devops_ec2" {
  ami           = "ami-0c101f26f147fa7fd"
  instance_type = "t2.micro"

  lifecycle {
    postcondition {
      condition     = self.instance_state == "running"
      error_message = "Instance did not reach running state. Current state: ${self.instance_state}"
    }
  }
}
```

**Behind the scenes:**
```
terraform apply
→ Instance created
→ Terraform checks: self.instance_state == "running"?
→ If NO → Error: Instance did not reach running state
→ Apply fails, Terraform attempts rollback
→ If YES → Apply complete
```

### When to use
- `precondition` — validate variable values, check AMI exists in region, enforce naming conventions
- `postcondition` — confirm instance is running, verify endpoint is reachable, validate output values

## Combined example — production-grade EC2

```hcl
variable "instance_type" {
  default = "t2.micro"
}

resource "aws_key_pair" "devops_kp" {
  key_name   = "devops-kp"
  public_key = tls_private_key.devops_kp.public_key_openssh
}

resource "aws_instance" "devops_ec2" {
  ami           = "ami-0c101f26f147fa7fd"
  instance_type = var.instance_type
  key_name      = aws_key_pair.devops_kp.key_name

  tags = {
    Name        = "devops-ec2"
    Environment = "production"
  }

  lifecycle {
    # 1. zero-downtime AMI replacement
    create_before_destroy = true

    # 2. protect from accidental deletion
    prevent_destroy = true

    # 3. ignore external tag drift (added by other tools)
    ignore_changes = [
      tags["LastDeployedAt"],
      tags["PatchedBy"],
    ]

    # 4. replace instance if key pair rotates
    replace_triggered_by = [
      aws_key_pair.devops_kp.id
    ]

    # 5. validate instance type before apply
    precondition {
      condition     = contains(["t2.nano", "t2.micro", "t2.small"], var.instance_type)
      error_message = "Only t2.nano/micro/small allowed. Got: ${var.instance_type}"
    }

    # 6. confirm running state after apply
    postcondition {
      condition     = self.instance_state == "running"
      error_message = "Instance not running after apply: ${self.instance_state}"
    }
  }
}
```

## Complete comparison table

| Argument | Triggers on | AWS API behavior | Resource ID | Downtime | Use case |
|---|---|---|---|---|---|
| `create_before_destroy = true` | ForceNew attribute change | Create new → delete old | New ID | Zero (brief overlap) | Production replacements |
| `create_before_destroy = false` (default) | ForceNew attribute change | Delete old → create new | New ID | Yes (gap) | Dev/test environments |
| `prevent_destroy = true` | Any destroy attempt | **Errors before API call** | Unchanged | N/A | Production databases, KMS keys |
| `ignore_changes = [attr]` | Drift on listed attrs | No API call (drift ignored) | Unchanged | None | ASG, external tools, tags |
| `ignore_changes = all` | Any drift | No API call ever | Unchanged | None | Legacy/unmanaged resources |
| `replace_triggered_by = [X]` | Change in resource X | Destroy + recreate this resource | New ID | Yes (unless +CBD) | Cross-resource dependencies |
| `precondition` | Before apply | **Errors before API call** | N/A | N/A | Input validation |
| `postcondition` | After apply | **Errors after resource created** | Created, then rolled back | N/A | Output validation |

---

## Decision guide — which lifecycle rule to add?

```
"I changed an immutable attr and don't want downtime"
  → create_before_destroy = true

"This resource must never be accidentally deleted"
  → prevent_destroy = true

"An external tool manages this attribute — stop reverting it"
  → ignore_changes = [that_attribute]

"I only want Terraform to create this, never update"
  → ignore_changes = all

"When resource X changes, this resource must be replaced too"
  → replace_triggered_by = [X]

"Validate inputs before wasting time on a failing apply"
  → precondition { condition = ... }

"Confirm the resource is healthy after it's created"
  → postcondition { condition = self.attr == expected }

"Zero-downtime replacement AND protect from deletion"
  → combine create_before_destroy + prevent_destroy
```
