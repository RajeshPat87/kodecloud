# Terraform — Attach Elastic IP to EC2 Instance (`aws_eip_association`)

## Concept / purpose

An **Elastic IP association** is the act of binding an allocated EIP to a specific EC2 instance (or network interface). Without the association, the EIP exists in your account but is unattached — it floats free, costs money, and does nothing.

**Three separate concepts:**
```
aws_eip              → allocates the EIP (reserves the public IP in your account)
aws_instance         → the EC2 instance to attach it to
aws_eip_association  → the binding between the two
```

**Why a separate resource (`aws_eip_association`) instead of using `instance =` inside `aws_eip`?**

You can technically put `instance = aws_instance.ec2.id` inside the `aws_eip` block — but it creates a tight coupling. The separate `aws_eip_association` resource is preferred because:
- The EIP and instance can be managed independently
- You can detach/reattach without destroying either resource
- The association has its own lifecycle — destroy the association to detach, without losing the EIP or the instance
- Cleaner when the EIP and instance are in different Terraform modules

**What happens at the AWS level when you associate:**
```
Before: Instance has dynamic public IP (changes on stop/start)
After:  Instance has the static EIP (persists across stop/start)
        The dynamic public IP is released when EIP is associated
```

**VPC vs EC2-Classic:**
- In VPC (all modern AWS), use `aws_eip_association` with `instance_id` and `allocation_id`
- `allocation_id` = the EIP's AWS allocation ID (starts with `eipalloc-`)
- `instance_id` = the EC2 instance ID (starts with `i-`)

## Syntax reference

```hcl
resource "aws_eip_association" "<local_name>" {
  instance_id   = "<instance-id>"           # REQUIRED — EC2 instance ID
  allocation_id = "<eipalloc-id>"           # REQUIRED for VPC EIPs

  # OR attach to a network interface instead of instance directly
  # network_interface_id = "<eni-id>"
  # private_ip_address   = "<private-ip>"   # optional — specific private IP to associate
}
```

**Reference pattern (when both resources are in the same main.tf):**
```hcl
resource "aws_eip_association" "<local_name>" {
  instance_id   = aws_instance.<ec2_name>.id
  allocation_id = aws_eip.<eip_name>.allocation_id   # note: allocation_id not id
}
```

## Watch-outs

- **`allocation_id` not `id`** — for `aws_eip`, the `.id` attribute is the **public IP address** (a string like `"54.x.x.x"`). The `allocation_id` is the AWS allocation ID (`"eipalloc-xxx"`). `aws_eip_association` requires `allocation_id` — using `.id` will fail with an invalid parameter error.
- **Don't add `instance =` inside `aws_eip`** — the `instance` argument inside `aws_eip` also creates an association, but it conflicts with a separate `aws_eip_association` resource. Use one or the other, not both.
- **VPC instances need `allocation_id`** — classic EC2 (retired) used `public_ip`. Modern VPC instances always use `allocation_id`.
- **EIP `domain = "vpc"`** — your existing `aws_eip` block doesn't set `domain = "vpc"` but it should for modern AWS. LocalStack accepts it either way, but in real AWS you'd get a warning. For this task it works as-is.
- **Association is separate from EIP lifecycle** — destroying `aws_eip_association` detaches the EIP but keeps both the EIP allocated and the instance running. The EIP then becomes unassociated (and starts costing money if left detached in real AWS).
- **One change only** — the task says "update main.tf." You're only adding one new block; the existing `aws_instance` and `aws_eip` resources stay exactly as they are.
